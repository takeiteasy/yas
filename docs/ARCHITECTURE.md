# Architecture

yas is a tree-walking (explicit-stack) interpreter: tagged-union values, a
mark-sweep GC, and an R7RS-ish module system layered over a small C core.
This document is the map for anyone changing the interpreter itself; see
[AOT.md](AOT.md) for the compile-time lowering pass and
[EMBEDDING.md](EMBEDDING.md) for the C embedding API.

## Source layout

Interpreter sources live in `src/`; the AOT compiler proper lives in
`aot/` (see below and [AOT.md](AOT.md)). `stdlib.h` is generated by
`embed.py` from `std/yas/*.ys` (see [BUILDING.md](BUILDING.md)) and is
not tracked in git.

| File | Role |
|---|---|
| `yas.h` | The only header: `struct YasAtom`, all object structs, every public prototype. |
| `data.c` | Constructors, symbol/keyword interning, list utilities, hash/vector ops, metatables, GC. |
| `read.c` | Lexer + recursive-descent reader: literals, reader conditionals, string interpolation. |
| `eval.c` | Environments, closures, the explicit-stack evaluator, special forms, `try`/`catch`, `call/cc`. |
| `builtin_core.c` | Pairs/list core: `car`/`cdr`/`cons`, `eq?`, `procedure?`, `length`, `append`, plus `throw`/`error` and the `raise_error` helper used by every builtin. |
| `builtin_vectors.c` | Numeric + SIMD arithmetic: `+ - * /` `=` `<` (incl. vec2/3/4 operands), `number->string`, the `float?`/`integer?` predicates, and every `vec*`/`mat4*` builtin together with the `vec4_*` SIMD helpers. |
| `builtin_vector.c` | Container `vector` builtins: `make-vector`, `vector-ref`, `vector-set!`, `vector-length`, `vector-append`, `vector?`. |
| `builtin_hash.c` | `hash` builtins (`make-hash`, `hash-ref`, ...) plus the metatable accessors. |

| `builtin_output.c` | `print` and `->string`. |

compiler, ordinary plain C built into both `yas` and `libyas` alongside
everything above - see [AOT.md](AOT.md).

## Value representation

No NaN-boxing: `struct YasAtom` (`yas.h`) is a 16-byte tagged union, an enum
tag plus a value union, passed **by value** everywhere:

```c
struct YasAtom {
	enum { YAS_ATOM_TYPE_NIL, YAS_ATOM_TYPE_PAIR, YAS_ATOM_TYPE_SYMBOL,
	       YAS_ATOM_TYPE_INTEGER, YAS_ATOM_TYPE_FLOAT, YAS_ATOM_TYPE_STRING,
	       YAS_ATOM_TYPE_VECTOR, YAS_ATOM_TYPE_HASH, YAS_ATOM_TYPE_PORT,
	       YAS_ATOM_TYPE_BYTEVECTOR, YAS_ATOM_TYPE_BUILTIN,
	       YAS_ATOM_TYPE_CLOSURE, YAS_ATOM_TYPE_MACRO,
	       YAS_ATOM_TYPE_CONTINUATION, YAS_ATOM_TYPE_CHAR,
	       YAS_ATOM_TYPE_KEYWORD, YAS_ATOM_TYPE_VEC2, YAS_ATOM_TYPE_VEC3,
	       YAS_ATOM_TYPE_VEC4, YAS_ATOM_TYPE_MAT4,
	       /* + YAS_ATOM_TYPE_FFI_* under YAS_FFI */ } type;
	union { struct YasPair *pair; const char *symbol; long integer;
	        double floatval; char *string; /* ... */ } value;
};
struct YasPair { struct YasAtom atom[2]; };
```

`yas_car`/`yas_cdr` are macros (`yas.h:201`); `yas_nil` is a
`static const YasAtom`. Closures, macros, and continuations are not
distinct struct types - they are pair chains with a rewritten `type` tag:

- `make_closure` builds `(env . (args . (docstring . body)))` and sets
  `type = YAS_ATOM_TYPE_CLOSURE`.
- `defmacro` builds the identical shape and sets `type = YAS_ATOM_TYPE_MACRO`.
- A continuation is a snapshot of the evaluator's stack pair chain with
  `type = YAS_ATOM_TYPE_CONTINUATION`.

SIMD `vec2`/`vec3`/`vec4`/`mat4` types select SSE, NEON, or WASM SIMD
intrinsics at compile time via `yas.h`'s platform detection, falling back
to scalar arrays.

## Reader

`yas_read_expr()` (`read.c`) is the single entry point. Notable behavior:

- **Every symbol is uppercased.** `car` reads as the symbol `CAR`. Anything
  that compares symbol names, mangles them, or interns them (including
  [AOT.md](AOT.md)'s name mangling) must account for this.
- Numbers: `0x`/`0b` prefixes; a `.` makes a literal a float.
- Quote forms: `'x` -> `(QUOTE x)`; `` `x `` -> `(QUASIQUOTE x)` (itself a
  runtime macro, see below); `,x`/`,@x` -> `(UNQUOTE x)`/`(UNQUOTE-SPLICING
  x)`.
- Literals: `#(...)` vector, `#vec(...)` / `#mat(...)` SIMD types,
  `#hash(...)` (keyword keys convert to symbols), `#\c` chars (named,
  `\x`/`\u`/`\U`, or raw UTF-8).
- **String interpolation** (`"Hello {{name}}"`) is desugared by the reader
  into `(STRING-APPEND ...)`.
- **Reader conditionals** `#+feature expr` / `#-feature expr` evaluate
  against `yas_init_features()`'s platform/feature list (`MACOS`/`LINUX`/
  `WINDOWS`/`BSD`, `UNIX`, arch names, `FFI`) and return `YAS_ERROR_SKIP`
  for excluded forms.

`YAS_ERROR_SKIP` is reader-internal, not a real error, and must be treated
as "skip this form, keep reading" rather than "stop reading". `main.c`'s
`load_file()` loop and `yas_eval_source()` (`eval.c`) both handle this
correctly (`if (read_err == YAS_ERROR_SKIP) continue;`), so a top-level
`#+`/`#-` form that excludes an expression does not truncate the rest of
the file, whichever entry point loaded it.

## Evaluator

`yas_eval_expr()` (`eval.c`) pushes an `EvalRoot` and calls `eval_vm()`, a
`do {} while` loop over an explicit heap-allocated stack of 6-element
frames (`parent`, `env`, `op`, `pending-args`, `evaluated-args`, `body`).

**Special forms** are matched by `strcmp` on the operator symbol inside
`eval_vm()` and are therefore unshadowable by any binding: `QUOTE`,
`DEFINE`, `LAMBDA`, `IF`, `TRY` (parses `CATCH`/`FINALLY` inline),
`DEFMACRO`, `APPLY`, `SET!`, `MACROEXPAND-1`, `CALL/CC`, `INCLUDE`/
`INCLUDE-CI`, `DEFINE-LIBRARY`, `IMPORT`.

Everything else familiar from Scheme - `begin`, `let`, `let*`, `cond`,
`and`, `or`, `when`, `unless`, `quasiquote`, `while`, `dotimes`, `dolist`,
`for`, `assert` - is a **runtime `defmacro`** defined in `std/yas/base.ys`,
expanded lazily during evaluation (a macro-tagged operand is retagged to a
closure, bound, and its expansion replaces the original expression). There
is no separate macro-expansion pass: expansion is interleaved with
evaluation and scoped per-environment, which is why an AOT/static
compilation pass can't simply "expand macros first" - it would need to
either drive the interpreter or reimplement this system.

**Tail calls**: the last form in a body is evaluated after the frame is
popped, and `if` rewrites the current expression in place rather than
recursing - so named-let loops are iterative. **`try` is the exception**:
it recurses into `yas_eval_expr()` for its body/handlers, a real C-stack
boundary. Tail calls do not propagate through `try`, and continuations
captured inside a `try` cannot be invoked across it.

**Lambda lists** are richer than plain Scheme: positional, optional-with-
default (`[x default]`), keyword args (`:KW [var default]`), and a
`. rest` tail. A leading string in the body, if more body follows, is
taken as a docstring.

### call/cc

Continuations snapshot the evaluator's stack (a heap-allocated pair
chain); invoking one just swaps the live stack pointer to the saved chain.
Because the "stack" is an ordinary heap list rather than an actual call
stack, continuations are **re-entrant, not one-shot** - unlike many Scheme
implementations, a captured continuation can be invoked more than once.

### Metamethod dispatch

Arithmetic and comparison builtins are intercepted, not just called
directly: `eval_do_apply()` reroutes `yas_builtin_add`/`subtract`/`multiply`/
`divide`/`numeq`/`less` to `~add`/`~sub`/`~mul`/`~div`/`~eq`/`~lt` when
either operand is a `YasHash` carrying that metamethod, and similarly
routes hash `~get`/`~set` and `~call`/`~missing` for operator-overloaded
hashes. **Any code path that calls a `YasBuiltin` function pointer directly
bypasses this** - relevant to anything (like AOT lowering) that wants to
lower arithmetic to a primitive C operation instead of going through the
evaluator.

## GC

Unified incremental tricolor mark-sweep - one `struct YasGCHeader`
(color/next/type) embedded in every heap type, one intrusive list, one
generic mark/sweep, instead of ten near-identical per-type copies.
`gc_alloc()` paces steps itself in bounded slices, driven by a live-byte
debt counter rather than a cons counter - allocation is what advances the
collector, not `eval_vm()`'s loop. `gc_mark_roots()` walks `eval_roots`,
`yas_ctx_exception`, `yas_library_registry`, `yas_global_search_paths`,
`yas_global_features`, and the root-registration shadow stack below. The
symbol/keyword intern tables (`data.c`) are plain `malloc`, not
GC-managed, so they are not part of this root set - see "Symbols" below.

Full design - the phase state machine, the write barrier, the
allocate-during-sweep hazard and how it's avoided, and worked examples -
lives in [GC.md](GC.md). Two things worth knowing before writing code
that holds `YasAtom`s across allocation points:

- **A root-registration API exists**: `yas_gc_push_root(YasAtom *slot)` /
  `yas_gc_pop_roots(int n)` (`yas.h`). Any native builtin or embedder
  holding a `YasAtom` local across a call that might allocate should use
  it - see [GC.md](GC.md#root-registration-api) for the API and a real
  bug this fixed during development. `eval_roots` itself stays internal
  to `eval.c`, rooting only `eval_vm()`'s own locals; the two root
  sources are walked together.
- **FFILibrary and FFIPointer are deliberately not GC-managed.** A raw
  `void*` has no recoverable ownership: it may be a `dlsym` result, an
  interior pointer into a `YasFFIStructInstance`, or a genuinely owned
  `ffi-malloc` block, and closing a library when its atom becomes
  unreachable could invalidate a still-live `YasFFIFunction` extracted
  from it (it doesn't hold a reference back to its library). Both stay
  explicitly managed via `ffi-close`/`ffi-free`.
- `yas_gc_mark()` traces `YAS_ATOM_TYPE_CONTINUATION` the same way as
  `YasPair`/`Closure`/`Macro` (it shares the same underlying
  allocation), so a continuation reachable only through application
  state is protected from collection like any other live value.
  `aux/gc_continuation_stress.ys` regression-tests this: it captures a
  continuation, lets its `call/cc` unwind normally so the continuation is
  reachable only via a binding (not the live evaluator stack), forces
  `(gc)` cycles, then invokes it from a later top-level form - on
  unfixed code this segfaults.

## Module system

`yas_library_registry` (`module.c`) is a `YasHash` keyed by strings like
`"yas/base"` (built from `(yas base)` via `yas_library_name_to_string()`,
which lowercases and slash-joins). A library record is itself a `YasHash`
holding `*name*`, `*env*` (a fresh top-level environment), and
`*exports*` (external-symbol -> internal-symbol).

`yas_library_load()` resolves a name in order:

1. Already registered -> return it.
2. Matches a native module (`yas/base`, `yas/hash`, `yas/vector`,
   `yas/text`, `yas/io`, `yas/math`, and `yas/ffi` under `YAS_FFI`) -> run
   its C loader, then layer the same key's embedded `.ys` source (if any)
   on top via `yas_eval_source()`. This is how e.g. `yas/base` gets `CAR`
   through `APPEND` from C and `map`/`cond`/`let`/`for` from
   `base.ys` in the same namespace.
3. A pure-Lisp stdlib entry (`yas/format` has no C loader) ->
   `yas_eval_source()` the embedded source directly.
4. Filesystem: search `yas_global_search_paths` (default `("./lib" ".")`)
   for `<dir>/<lib/path>.ys`, resolve with `realpath`, `yas_eval_file()` it.

`yas_module_import()` supports `(only ...)`, `(except ...)`, `(prefix ... p)`,
and `(rename ... (old new))`; otherwise it copies every export into the
importing environment via `yas_env_define()`. **Imports are flat copies
into an alist environment - there is no namespace object at runtime.**

`yas_module_define_library()` handles `(export ...)` (with `(rename int
ext)`), `(import ...)` into the library's own environment, `(begin ...)`
evaluated in that environment, and `(include "file")`.

## Environments

`(parent . ((sym . val) (sym . val) ...))` - alists of alists. `yas_env_get()`
is a linear scan of the current frame, then a recursive walk to the
parent; `yas_env_define()` scans-and-mutates-or-conses. Every variable
reference is O(frame depth x frame size); there is no slot resolution.

## Symbols

Interned by `strdup`'d string identity in an open-addressed hash table
(`data.c`, one for symbols and a parallel one for keywords - FNV-1a over
the string, linear probing, grow-and-rehash at 70% load, no deletes so no
tombstones). `yas_make_sym()`/`yas_make_keyword()` are O(1) amortized.
Both tables are plain `malloc`, not GC-managed - the interned strings are
immortal for the process lifetime, so there is nothing here for the
collector to trace and no GC root needed (unlike everything else
`gc_mark_roots()` walks, above). Symbol comparison everywhere else is
pointer equality, not `strcmp` - the interning is what makes that valid.
A side effect: `yas_make_sym()` no longer allocates on the GC heap, so it
is no longer a GC-stepping trigger for every token the reader produces
(see [GC.md](GC.md)'s "Allocation-triggered stepping").

## Arithmetic: interpreter vs. `yas/base`

Without any import, `+`/`-`/`*`/`/` are `yas_builtin_add`/etc.,
straightforward C arithmetic. **After `(import (yas base))`**,
`std/yas/base.ys` rebinds them:

```scheme
(define + (let ((old+ +)) (lambda xs (foldl old+ 0 xs))))
```

- variadic identity, going through `foldl` and allocating a rest-list per
  call. Same for `-`/`*`/`/`. This is the reason [AOT.md](AOT.md)'s
  lowering pass requires AOT input to *not* import `yas/base`: it treats
  `+`/`-`/`*`/`/` as C primitives, which is correct for the raw builtins
  but not for `yas/base`'s wrapped versions (which also carry the
  metamethod dispatch described above).

Also worth knowing: `yas_load_math_library()` registers no numeric builtins at
all beyond vec/mat operations - `sqrt`, `abs`, `quotient`, `remainder`,
`modulo` are all interpreted Lisp in `std/yas/math.ys`, not C.
