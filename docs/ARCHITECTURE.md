# Architecture

yas is a tree-walking (explicit-stack) interpreter: tagged-union values, a
mark-sweep GC, and an R7RS-ish module system layered over a small C core.
This document is the map for anyone changing the interpreter itself; see
[AOT.md](AOT.md) for the compile-time lowering pass and
[EMBEDDING.md](EMBEDDING.md) for the C embedding API.

## Source layout

All sources live in `src/`. `stdlib.h` is generated by `embed.py` from
`std/yas/*.ys` (see [BUILDING.md](BUILDING.md)) and is not tracked in git.

| File | Role |
|---|---|
| `lisp.h` | The only header: `struct Atom`, all object structs, every public prototype. |
| `data.c` | Constructors, symbol/keyword interning, list utilities, hash/vector ops, metatables, GC. |
| `read.c` | Lexer + recursive-descent reader: literals, reader conditionals, string interpolation. |
| `eval.c` | Environments, closures, the explicit-stack evaluator, special forms, `try`/`catch`, `call/cc`. |
| `builtin.c` | Every `Builtin` implementation, plus SIMD helpers and serialize/deserialize. |
| `module.c` | Library registry, native module registration, `import`/`define-library`, stdlib loading. |
| `print.c` | `print_expr` (stdout) and `sprint_expr` (two-pass string rendering). |
| `io.c` | I/O sandbox (allow/deny globs), virtual-filesystem providers, `struct Port`, `slurp()`. |
| `ffi.c` | libffi bindings, compiled only under `YAS_FFI`. |
| `utf8.c` | UTF-8 decode/encode/length/indexing. |
| `aot_shim.c` / `aot_plan.c` | The AOT reader front end and plan compiler - see [AOT.md](AOT.md). |
| `main.c` | REPL and file-loading CLI entry point. |

## Value representation

No NaN-boxing: `struct Atom` (`lisp.h`) is a 16-byte tagged union, an enum
tag plus a value union, passed **by value** everywhere:

```c
struct Atom {
	enum { AtomType_Nil, AtomType_Pair, AtomType_Symbol, AtomType_Integer,
	       AtomType_Float, AtomType_String, AtomType_Vector, AtomType_Hash,
	       AtomType_Port, AtomType_Bytevector, AtomType_Builtin,
	       AtomType_Closure, AtomType_Macro, AtomType_Continuation,
	       AtomType_Char, AtomType_Keyword,
	       AtomType_Vec2, AtomType_Vec3, AtomType_Vec4, AtomType_Mat4,
	       /* + AtomType_FFI* under YAS_FFI */ } type;
	union { struct Pair *pair; const char *symbol; long integer;
	        double floatval; char *string; /* ... */ } value;
};
struct Pair { struct Atom atom[2]; };
```

`car`/`cdr` are macros (`lisp.h:175`); `nil` is a `static const Atom`.
Closures, macros, and continuations are not distinct struct types - they
are pair chains with a rewritten `type` tag:

- `make_closure` builds `(env . (args . (docstring . body)))` and sets
  `type = AtomType_Closure`.
- `defmacro` builds the identical shape and sets `type = AtomType_Macro`.
- A continuation is a snapshot of the evaluator's stack pair chain with
  `type = AtomType_Continuation`.

SIMD `vec2`/`vec3`/`vec4`/`mat4` types select SSE, NEON, or WASM SIMD
intrinsics at compile time via `lisp.h`'s platform detection, falling back
to scalar arrays.

## Reader

`read_expr()` (`read.c`) is the single entry point. Notable behavior:

- **Every symbol is uppercased.** `car` reads as the symbol `CAR`. Anything
  that compares symbol names, mangles them, or interns them (including
  [AOT.md](AOT.md)'s name mangling) must account for this.
- Numbers: `0x`/`0b` prefixes; a `.` makes a literal a float.
- Quote forms: `'x` -> `(QUOTE x)`; `` `x `` -> `(QUASIQUOTE x)` (itself a
  runtime macro, see below); `,x`/`,@x` -> `(UNQUOTE x)`/`(UNQUOTE-SPLICING
  x)`.
- Literals: `#(...)` vector, `#vec(...)` / `#mat(...)` SIMD types,
  `#hash(...)` (keyword keys convert to symbols), `#\c` chars (named,
  `\x`/`\u`/`\U`, or raw UTF-8).
- **String interpolation** (`"Hello {{name}}"`) is desugared by the reader
  into `(STRING-APPEND ...)`.
- **Reader conditionals** `#+feature expr` / `#-feature expr` evaluate
  against `init_features()`'s platform/feature list (`MACOS`/`LINUX`/
  `WINDOWS`/`BSD`, `UNIX`, arch names, `FFI`) and return `Error_Skip` for
  excluded forms.

`Error_Skip` is reader-internal, not a real error, and must be treated as
"skip this form, keep reading" rather than "stop reading". `main.c`'s
`load_file()` loop handles this correctly (`if (read_err == Error_Skip)
continue;`); **`eval_source()` does not** - it treats any read error with
an empty message (which `Error_Skip` produces) as EOF and stops, silently
truncating the rest of the file. This affects anything that loads code via
`eval_source()` - including `library_load()` for stdlib/native modules -
whenever the loaded source contains a top-level `#+`/`#-` form that
excludes an expression. `src/aot_shim.c`'s reader front end for the AOT
pass replicates `main.c`'s loop, not `eval_source()`'s, specifically to
avoid this.

## Evaluator

`eval_expr()` (`eval.c`) pushes an `EvalRoot` and calls `eval_vm()`, a
`do {} while` loop over an explicit heap-allocated stack of 6-element
frames (`parent`, `env`, `op`, `pending-args`, `evaluated-args`, `body`).

**Special forms** are matched by `strcmp` on the operator symbol inside
`eval_vm()` and are therefore unshadowable by any binding: `QUOTE`,
`DEFINE`, `LAMBDA`, `IF`, `TRY` (parses `CATCH`/`FINALLY` inline),
`DEFMACRO`, `APPLY`, `SET!`, `MACROEXPAND-1`, `CALL/CC`, `INCLUDE`/
`INCLUDE-CI`, `DEFINE-LIBRARY`, `IMPORT`.

Everything else familiar from Scheme - `begin`, `let`, `let*`, `cond`,
`and`, `or`, `when`, `unless`, `quasiquote`, `while`, `dotimes`, `dolist`,
`for`, `assert` - is a **runtime `defmacro`** defined in `std/yas/base.ys`,
expanded lazily during evaluation (a macro-tagged operand is retagged to a
closure, bound, and its expansion replaces the original expression). There
is no separate macro-expansion pass: expansion is interleaved with
evaluation and scoped per-environment, which is why an AOT/static
compilation pass can't simply "expand macros first" - it would need to
either drive the interpreter or reimplement this system.

**Tail calls**: the last form in a body is evaluated after the frame is
popped, and `if` rewrites the current expression in place rather than
recursing - so named-let loops are iterative. **`try` is the exception**:
it recurses into `eval_expr()` for its body/handlers, a real C-stack
boundary. Tail calls do not propagate through `try`, and continuations
captured inside a `try` cannot be invoked across it.

**Lambda lists** are richer than plain Scheme: positional, optional-with-
default (`[x default]`), keyword args (`:KW [var default]`), and a
`. rest` tail. A leading string in the body, if more body follows, is
taken as a docstring.

### call/cc

Continuations snapshot the evaluator's stack (a heap-allocated pair
chain); invoking one just swaps the live stack pointer to the saved chain.
Because the "stack" is an ordinary heap list rather than an actual call
stack, continuations are **re-entrant, not one-shot** - unlike many Scheme
implementations, a captured continuation can be invoked more than once.

### Metamethod dispatch

Arithmetic and comparison builtins are intercepted, not just called
directly: `eval_do_apply()` reroutes `builtin_add`/`subtract`/`multiply`/
`divide`/`numeq`/`less` to `~add`/`~sub`/`~mul`/`~div`/`~eq`/`~lt` when
either operand is a `Hash` carrying that metamethod, and similarly routes
hash `~get`/`~set` and `~call`/`~missing` for operator-overloaded hashes.
**Any code path that calls a `Builtin` function pointer directly bypasses
this** - relevant to anything (like AOT lowering) that wants to lower
arithmetic to a primitive C operation instead of going through the
evaluator.

## GC

Mark-sweep, triggered on an allocation counter inside `eval_vm()` (every
100,000 conses). `gc_mark()` walks from `eval_roots`, `ctx_exception`,
`sym_table`, `kw_table`, `library_registry`, `global_search_paths`, and
`global_features`, then `gc()` sweeps pairs, vectors, hashes, strings,
ports, bytevectors, vec2/3/4, mat4, and (when built with `YAS_FFI`)
`FFIFunction`/`FFIStruct` instances. Each type past pairs/vectors/hashes
follows the same pattern: a `mark`/`next` pair embedded in (or, for the
bare-pointer types String/Vec2-4/Mat4, a small header wrapping) the
allocation, threaded through a global intrusive list that `gc()` sweeps.

Two things worth knowing before writing code that holds `Atom`s across
allocation points:

- **There is no root-registration API.** `EvalRoot`/`eval_roots` are
  `static` in `eval.c`, not exported via `lisp.h`. A native function (or a
  hypothetical AOT-generated function operating on live `Atom`s) that
  holds a local `Atom` across any call that can trigger `gc()` has no way
  to register it as a root. This is the reason [AOT.md](AOT.md)'s current
  lowering never produces an `Atom` - only unboxed `long`/`double`.
- **FFILibrary and FFIPointer are deliberately not GC-managed.** A raw
  `void*` has no recoverable ownership: it may be a `dlsym` result, an
  interior pointer into an `FFIStruct`, or a genuinely owned `ffi-malloc`
  block, and closing a library when its atom becomes unreachable could
  invalidate a still-live `FFIFunction` extracted from it (it doesn't hold
  a reference back to its library). Both stay explicitly managed via
  `ffi-close`/`ffi-free`.
- `AtomType_Continuation` is not among the types `gc_mark()` traces - a
  continuation value reachable only through application state, not
  through a marked root, is not protected from collection.

## Module system

`library_registry` (`module.c`) is a `Hash` keyed by strings like
`"yas/base"` (built from `(yas base)` via `library_name_to_string()`,
which lowercases and slash-joins). A library record is itself a `Hash`
holding `*name*`, `*env*` (a fresh top-level environment), and
`*exports*` (external-symbol -> internal-symbol).

`library_load()` resolves a name in order:

1. Already registered -> return it.
2. Matches a native module (`yas/base`, `yas/hash`, `yas/vector`,
   `yas/text`, `yas/io`, `yas/math`, and `yas/ffi` under `YAS_FFI`) -> run
   its C loader, then layer the same key's embedded `.ys` source (if any)
   on top via `eval_source()`. This is how e.g. `yas/base` gets `CAR`
   through `APPEND` from C and `map`/`cond`/`let`/`for` from
   `base.ys` in the same namespace.
3. A pure-Lisp stdlib entry (`yas/format` has no C loader) -> `eval_source()`
   the embedded source directly.
4. Filesystem: search `global_search_paths` (default `("./lib" ".")`) for
   `<dir>/<lib/path>.ys`, resolve with `realpath`, `eval_file()` it.

`module_import()` supports `(only ...)`, `(except ...)`, `(prefix ... p)`,
and `(rename ... (old new))`; otherwise it copies every export into the
importing environment via `env_define()`. **Imports are flat copies into
an alist environment - there is no namespace object at runtime.**

`module_define_library()` handles `(export ...)` (with `(rename int
ext)`), `(import ...)` into the library's own environment, `(begin ...)`
evaluated in that environment, and `(include "file")`.

## Environments

`(parent . ((sym . val) (sym . val) ...))` - alists of alists. `env_get()`
is a linear scan of the current frame, then a recursive walk to the
parent; `env_define()` scans-and-mutates-or-conses. Every variable
reference is O(frame depth x frame size); there is no slot resolution.

## Symbols

Interned by `strdup`'d string identity in a linear list (`data.c`);
`make_sym()` is an O(n) `strcmp` scan over the whole table on every new
symbol, with an equivalent parallel table for keywords. Symbol comparison
everywhere else is pointer equality, not `strcmp` - the interning is what
makes that valid.

## Arithmetic: interpreter vs. `yas/base`

Without any import, `+`/`-`/`*`/`/` are `builtin_add`/etc.,
straightforward C arithmetic. **After `(import (yas base))`**,
`std/yas/base.ys` rebinds them:

```scheme
(define + (let ((old+ +)) (lambda xs (foldl old+ 0 xs))))
```

- variadic identity, going through `foldl` and allocating a rest-list per
  call. Same for `-`/`*`/`/`. This is the reason [AOT.md](AOT.md)'s
  lowering pass requires AOT input to *not* import `yas/base`: it treats
  `+`/`-`/`*`/`/` as C primitives, which is correct for the raw builtins
  but not for `yas/base`'s wrapped versions (which also carry the
  metamethod dispatch described above).

Also worth knowing: `load_math_library()` registers no numeric builtins at
all beyond vec/mat operations - `sqrt`, `abs`, `quotient`, `remainder`,
`modulo` are all interpreted Lisp in `std/yas/math.ys`, not C.
